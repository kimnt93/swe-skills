### playbook-build

The default pipeline of a CTO/CEO: issue, plan, code, PR, review and fix, merge. (1) The CTO/CEO creates the issue card; (2) the architect plans it carefully and the CTO/CEO checks the plan against the card and accepts it; (3) each package of the plan becomes an issue the merge rules approve, and the role that holds its lane (developer, tester or devops) builds it in its own worktree, opens the PR and hands it over; (4) the reviewer reviews the code against the issue and the accepted plan, fixes what it finds within 3 rounds and passes or stops it, and the CTO/CEO trusts the verified PASS, merges, confirms and closes the card. Use for any request to build that names no other playbook. For one existing PR use playbook-ship; for only a plan, playbook-plan.

### playbook-plan

The planning pipeline for new features, cross-file changes and hard bugs: the CTO/CEO turns a problem into a planning card (an issue) on the repository and sends it through orchestration to the architect (a bot or a delegated worker); the architect analyses, compares approaches, recommends a design and stack, and comments it on the issue; the architect sends the result back to the CTO/CEO, who accepts it or asks for changes. It stops at acceptance: no code, no branch, no PR. Use when only a plan is wanted: asked to plan, design or analyse a problem before anyone builds it. To plan and build, use playbook-build (the default), whose stage 2 is these steps.

- **Invoke:** `/swe:playbook-plan`

- **References:**

  - `references/orchestration.md`: Orchestration
- **Assets:** `example`

### playbook-quick

The quick pipeline, only when a request names it: issue, code, PR, merge, with no check. No plan, no reviewer, no verdict and no feedback rounds. The CTO/CEO turns the problem into ready-to-build issues; each developer implements one in its own worktree, runs the issue's Done when, opens one PR, watches the required checks and sends it back; the CTO/CEO, without reading the diff or running the PR's commands, merges it only when the mechanical conditions hold (merge rules allow, required checks green, not behind and no conflict, the head is the reported SHA, not a money path), confirms, and the developer removes its worktree. When they cannot hold, the CTO/CEO stops it and the PR stays open. Never picked by itself: with no playbook named, use playbook-build.

- **Invoke:** `/swe:playbook-quick`

### playbook-review

Review one existing pull request and only comment: read the PR, its linked issue and diff, run its checks in a throwaway checkout when the code is safe to run, and post one PASS or FAIL verdict at the head SHA. No code change, no commit, no push, no merge, no close. Use when asked to review a PR. To also fix and merge it use playbook-ship; to build from a problem use playbook-build (the default).

- **Invoke:** `/swe:playbook-review`
- **Detail:** [router.md](skills/router.md#playbook-review) · **Source:** [SKILL.md](../src/skills/playbook-review/SKILL.md)

### playbook-ship

Take one existing pull request to main: the reviewer (a bot with its agents, or one agent a person asked) reviews it, fixes what it finds on the PR branch, reviews again for at most 3 rounds, then merges it and confirms the linked issue closed, or stops it with final feedback, leaving the PR open. Only for a PR whose issue is approved by the merge rules and that the reviewer did not write. Use when asked to ship, finish or land a PR, such as an open PR that playbook-quick stopped. For a comment-only review use playbook-review.

### playbook-test

No code is fixed, no branch, no PR, no merge. Use when asked to test, QA, verify or find bugs in a running app, site, API or tool; to build or fix something use playbook-build, the default.

### api-cli-testing

### bot-orchestration

How standing bots and the agents they start work together: who may message whom (bot to agent, agent back to its own bot, bot to bot to delegate and to report), never agent to agent. The CEO or CTO bot only orchestrates: it writes the issue and delegates it to the bot of its role (architect, developer, tester, devops, reviewer); the developer bot rates it simple, medium or hard, starts an agent on that row of the team's agent table, which builds it and opens the PR, then verifies the work and reports back. Use before delegating a job to another bot, before starting any agent as a bot, and when reporting back.

### service-errors

Report unexpected errors and panics from Go, Python and Rust services (and Next.js / Vite frontends) to Sentry or GlitchTip through the Sentry DSN (SENTRY_DSN, or SENTRY_DSN_FILE as a Swarm secret). Every error-level log line becomes one grouped event with the service name, environment, release and trace id, and nothing private - no request, user, breadcrumbs, local variables, exception text or log fields. Tested templates for Go, Python and Rust, with a local receiver that checks what a service really sends and a static audit. Use when adding or reviewing error tracking, Sentry, GlitchTip, panic capture or SENTRY_DSN in a service.

### service-logging

Set up unified structured JSON logging for services in Go (zerolog), Python (kimnt93/jlogger), TypeScript/JavaScript (pino) or Rust (tracing). Every line has level, development_environment, service_name, node_name, logger, an RFC 3339 nanosecond UTC time, caller as file:line, and optional OpenTelemetry trace_id and span_id, with identity read from SERVICE_NAME, DEVELOPMENT_ENVIRONMENT/ENV_NAME and NODE_NAME. Use when creating a service, adding or standardizing logging, replacing a custom logger, adding trace correlation to logs, or checking that log output matches the platform format and Loki labels.

### service-tracing

Add or review OpenTelemetry tracing in Go, Python, TypeScript/JavaScript or Rust services. Default mode traces service dependencies only - one stable service name per service plus boundary spans and W3C context propagation so the service graph (who calls whom over HTTP/gRPC, queues and datastores) is complete and verified. Detailed mode (internal spans, attributes, span links, log correlation, sampling tuning) only when the user asks for it. Includes tested templates, the tracing environment contract, a dependency scanner and a local OTLP verifier.
