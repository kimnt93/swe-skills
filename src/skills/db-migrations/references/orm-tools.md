# Migrations in an ORM project

The default does not change when a project uses an ORM ([db-orm](../../db-orm/SKILL.md)): the schema is goose SQL files, and the ORM
maps onto it. One database has **one** migration system.

| Project situation | What to do |
|---|---|
| New service, with or without an ORM | goose files in `schemas/` ([goose](goose.md)) |
| The project already runs the ORM's migration tool | keep it as the only system; write each migration as plain, readable SQL |
| The ORM would "generate the schema" | do not: write the SQL, then update the model |
| Two systems already exist | stop and ask which one owns the schema; never add a third |

## Existing tools

- **Alembic** (SQLAlchemy). Revisions are Python files; write the change with `op.execute("""...""")` in the multi-line SQL layout instead of
  autogenerated `op.add_column` chains, so it reads like a goose file. Autogenerate is a draft to review, never applied unread. Run
  `alembic upgrade head` in the one-shot job.
- **GORM `AutoMigrate`.** Never against a real database: it adds columns but cannot drop, rename or build concurrent indexes. Use it
  only to create a portable table in a SQLite test; the schema is goose files.
- **sea-orm-migration** (SeaORM). A separate migration crate; keep its steps small and prefer `execute_unprepared` with raw SQL for anything
  non-trivial. Run its `up` in the one-shot job.
- **bun/migrate** (uptrace/bun). Go or SQL migrations in a directory; prefer the SQL form. Run `Migrate` in the one-shot job.

In every case the rules in [safe-changes](safe-changes.md) apply unchanged: concurrent indexes, defaults, batches, expand and contract, and
Down or an `irreversible` note.

## Never

- `AutoMigrate`, `Base.metadata.create_all`, `Schema::create_table_from_entity` or `synchronize` against staging or production.
- Generating a migration from a model diff and applying it without reading the SQL.
- Running migrations from the application's start-up path on every replica.
