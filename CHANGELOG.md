# Changelog

`make publish` refuses a version without an entry here. This file holds the release notes of the current version only; it does
not track changes between versions.

## [Unreleased]

- **`build-slot`, one shared queue for heavy builds**: new skill whose `scripts/build-slot.py` (Python standard library only) runs a heavy build command (Cargo, maturin, `docker build`, native extensions) when one of the shared slots is free: 2 by default (`BUILD_SLOT_SLOTS`), in arrival order, one queue per user and machine in `~/.cache/build-slot` (`BUILD_SLOT_DIR`) that every installed copy shares. It sets `CARGO_BUILD_JOBS=6` only when unset (`BUILD_SLOT_JOBS`), prints the queue position to stderr, returns the command's exit code, has no wait limit unless `BUILD_SLOT_TIMEOUT` is set (then exit 75 without running) and never kills a running build. Liveness uses OS file locks, never PIDs: a dead waiter is skipped, Ctrl+C while waiting leaves the queue and a nested call reuses the outer slot. On Linux and macOS a killed wrapper leaves the slot held until its build ends; on Windows a Job Object ends the build with its wrapper. The router's done rule points to it. `tests/build_slot_test.py` runs in `make test` and on Linux, macOS and Windows in the `build-slot` GitHub Actions workflow.
- **Business rules belong to the project, not the plugin**: new principle `business-rules`, one short rule linked from the asking rule, the manager, reviewer and deployment skills and the four playbooks that merge (`build`, `quick`, `ship`, `solo`), also from the money-path principle, the router, the `github` merge step, the planner, intake and the project documents. A project's own agents file (such as `AGENTS.md`) or the operator's instructions state its business rules, such as blocked deploy or merge windows and which paths are high risk. They are read from the base branch before a merge or a deploy and obeyed; where two disagree the stricter holds until the person says which; a blocked window is waited out unless those rules or the person allow the step; **with none stated there is no window**. They may add high-risk paths, each held as a money path, and never remove a built-in one or weaken a safeguard, gate or stop. The page has a placeholder example only. No skill stated a window before this change, and **no script reads or checks business rules**: obeying them is the agent's duty.
- **Neutral examples**: examples and phrases from one business domain (hot-path and prompt examples, sample symbols, SQL, log and span tables, test data) are reworded, and the plugin manifest no longer has a domain keyword. No gate script, linter, label or stop changed: the money-path list, the replay proof and the testing runners' `trade` effect and risky words are as before.
- **`playbook-solo`, one agent from problems to merged pull requests, only when a request names it**: one agent writes the problems as issues and, for each in dependency order, makes its own worktree and branch, builds it with its tests, opens one PR, checks that head itself, merges it with `--rebase --match-head-commit`, confirms, closes the work and removes the worktree; one report at the end. It starts no other agent or bot and hands nothing over. Before a merge: the merge rules allow it, the `Done when` passes on the committed head, required checks are green, the branch is not behind and has no conflict, and the `security-review` check of the diff has no proven finding and no outbound data the accepted issue does not ask for. **That is a self-check, not an independent review**, and it posts no verdict. A money-path change stops with the PR open; a blocked issue stays open with its PR and branch while independent issues go on. It is the one case where a PR's author merges it. No gate script changed: `pr_loop.py can-merge` can allow no solo merge, so no script refuses one; `can-remove` keeps the worktree of a PR left open; and a bot neither runs nor delegates it. The CTO/CEO's default is still `playbook-build`.
- **Developers deliver the complete issue, with unit and functional tests (breaking)**: one pull request holds the feature, its unit tests and its functional tests (the behaviour through its real entry point with local or disposable dependencies), and the issue's `Done when` names both; where one kind cannot apply, such as docs only, the issue says `none:` with the reason and the PR says why. The `package` issue template and the PR template have the required lines `**Unit tests:**` and `**Functional tests:**`, so **an open package issue or PR body without them fails the linter until they are added**. No package, card or quick issue holds another's tests.
- **The tester only on request**: the tester role gets work only when a request asks for testing by name. No pipeline creates or sends a test package by default, developer tests are never moved to the tester, and a `test` lane issue nobody asked the tester for goes to the developer. `playbook-test` is unchanged as the requested path.
- **Agents work without needless questions**: one short rule for asking (the `never-block-on-the-human` principle), linked from the architect, planner, intake, manager, delegate, bot-orchestration, developer and reviewer skills and every playbook. The request covers its normal steps; a missing detail is looked up first; a reversible choice takes the recommended option and is recorded with its reason; extra work is not offered as a question. It still asks before money, trading, accounts or risk limits, anything irreversible, production changes and server writes, money-path merges, publishing or unasked outbound data, an outsider's issue and access only the owner can give; in one batch with recommendations, while unaffected work continues, and no reply is never approval. Roles send questions to the CTO/CEO, who never stands in for the owner's approval. The plan and epic-plan templates have a `Decisions` section; `Open Questions` holds only what must be asked. A plan can be accepted with a question waiting only when its design does not depend on the answer, and nothing that needs the answer starts. A staging deploy through a project's normal pipeline needs no question, within the project's deploy rules. No gate, merge check or playbook stop changed.
- **Security and outbound data on every reviewed pull request (breaking)**: `review`, `ship` and `build` require it besides correctness, for a pull request of any size. A pull request that adds or widens a way data leaves (HTTP and socket calls, webhooks, telemetry and analytics, error trackers, third-party SDKs, uploads, mail and chat, DNS, CI, install and build steps, a dependency that phones home) or sends more on one fails unless a linked accepted issue asks for that exact destination and data, and a proven security finding it brings in blocks the merge. Every `verdict` comment needs a `## Security` section (`Scan`, `Outbound data`, `Risk`, `Not checked`). `package_lint.py` requires it whatever a team's own template says, and `pr_loop.py decide` and `can-merge` refuse a PASS without it, with a proven finding, with a scan of another head or one that scanned nothing, with an outbound path nobody asked for, or with an `asked for by #n` line whose issue the pull request does not link or whose text does not hold the destination. A FAIL still counts without it. **An open pull request whose PASS has no such section is refused until it is reviewed again.** The new `issue_gate.py asked <issue> --pr <n>` prints the only issue text that can ask: of a linked, allowed issue, without HTML comments, neither written nor edited after the pull request's work started (its creation and commit dates) unless the owner accepted it since; anything unreadable refuses. The scripts check the section and its claims; finding everything and reading what an issue means stay the reviewer's judgment. `playbook-quick` is unchanged: it has no check.
- **`security-review`**: new skill with one page per topic (outbound data, secrets, input validation, injection, authentication and authorization, session and browser attacks, rate limits, logs and errors, dependencies and supply chain, files, commands and URLs with SSRF, money and chain code, CI and containers, agent and prompt code), each with what to look for, a bad and a good example and how to prove it on your own machine. `scripts/security_scan.py` lists secrets (rule, file and line, never a value), outbound destinations (host only) and calls, files that already send and gained lines, dependencies and install steps, risky patterns, removed controls and what it could not read, from a diff, two commits or a whole tree. It imports no network module, starts only read-only local git with fetching off, prints no line of the diff and exits 2 when it could not scan. It is an aid with line rules: a clean scan is never a pass.
- **`playbook-security`**: new pipeline, a security audit on request of a pull request or a repository: scan, every outbound path with the issue that asks for it, findings proven by a command locally and never against a live system, and a report with issues ready to file. It changes no code, posts no verdict, merges nothing and files nothing unasked.

- **Orca only (breaking)**: the stack runs in Orca: Orca (workspaces, worktrees, orchestration), Orca bots (standing role holders that orchestrate) and harnesses (the coding CLIs Orca runs agents in). The T3 Code paths and the direct headless CLI relay are removed with their references, scripts, config keys and checks, as are the tmux runner (`cli/bin/delegate`), its briefs, templates, per-CLI configs and the example projects. The plugin still installs into every harness it supported. The documentation pages that described the removed runner are gone, and the runbooks are now: fill the agent table, install locally, publish.
- **One agent table (breaking)**: the CTO/CEO holds one table with the rows `simple`, `medium`, `hard` and `planner/architect`, each a harness, a model and a reasoning effort. The repository ships the empty template (`bot-orchestration/assets/agent-table.template.md`); each team fills its own copy outside the repository. `agent_table.py` (`path`, `check`, `row`, `init`) reads it, and a missing table, row or cell stops and asks: there is no default. Every brief carries `Row:` and `Run on:`, every handoff the agent-table line. It replaces the routing tier table, the router's model tiers, the agent models in `config.json` (now only `{"agent_table": ""}`), the delegate defaults, the subagents' build-time models, the plan's `agent` and `reviewer` fields (now `difficulty`) and `swe-cli models`.
- **Exactly nine playbooks, and every one that builds ends with the merge** (a money path, a refusal or a stop leaves the PR open): `playbook-build` (the default), `playbook-quick` and `playbook-solo` (each only when a request names it), `playbook-plan`, `playbook-refactor-plan`, `playbook-review`, `playbook-ship`, `playbook-test` and `playbook-security`. A request that names a playbook follows it; a CTO/CEO told none uses `build`. `swe-cli playbooks` lists the nine. The old suite (`playbook-deliver`, `playbook-feature`, `playbook-bugfix`, `playbook-cifix`, `playbook-docs`, `playbook-rebase`, `playbook-land`, `playbook-changelog`, `playbook-verify` and the old solo pipeline, which shares only its name with today's), the `play-*` shortcuts and the `playbook` dispatcher are removed; their methods live in the skills they named.
- **One child chat per parent chat and receiving bot**: the first delegation from a chat to a bot uses `--chat new` with the parent chat's name as the subject; the sender records the new chat's id where a resumed run can read it, and every later message from that chat to that bot (the next job, follow-ups, changes, merged, stopped) uses `--chat` with it, never the bot's Home Chat. Another parent chat gets its own; a bot that delegates further does the same under the same subject (the delegate template says so); a chat that is gone, unknown or ambiguous is replaced by a new one carrying the context, never guessed. A status still goes to the return address. `build` and `quick` no longer open a chat per issue. `tests/enforcement_test.sh` refuses a documented send to a bot without such a `--chat`. Not tried: sending while the child chat is busy, and chains of more than one child chat.
- **Testing as a user**: `playbook-test` is testing only: the tester writes the expected result of every step before running, uses the software as its user does, runs each failure again and returns a short report with pass or fail per function, evidence paths and bugs ready to file; it fixes no code, opens no pull request, merges nothing and files issues only when asked. `web-testing` drives a real browser (Playwright, pinned; needs `uv` and `ffmpeg`) with real clicks and keystrokes and records, per step, the input, the expected result, the observed output and a screenshot, and per click a video until the answer arrived, key frames named by their time and an analysis of timing, console errors, failed requests and slow or missing answers. `api-cli-testing` does the same for an HTTP API or a command-line tool. Both runners test only allowed hosts and programs; on production a step that changes something runs only when approved by name; credentials come from the environment and are cut out of every text file; evidence must be outside every git work tree. The self-tests and `tests/testing_skills_test.sh` run them against a local fixture app with working, broken, slow and dead functions (`--browser` adds the web run).
- **Build**: issue → plan → code → PR → review and fix → merge. The CTO/CEO writes the card; the architect plans it carefully and the CTO/CEO checks the plan against the card before accepting it; each package issue is built by the developer (devops for `ops`; the tester only on request) in its own worktree, which opens one PR and hands it over; the reviewer checks the code against the issue and the accepted plan (packages, contracts, owned files, verify commands; a departure is a finding), fixes its findings in at most 3 rounds, and the CTO/CEO trusts a verified PASS, merges and closes the card when every child is merged, or reports the stop. A "where does this run stand" table read from GitHub tells a resumed run its stage. By default the owner approves and reviews no code; a `risk:money-path` change is never merged automatically.
- **Quick has no check**: issue → code → PR → merge, with no plan, reviewer, verdict or feedback rounds. Each issue the CTO/CEO creates for it carries the header line `Pipeline: quick`, which counts only when every line before the first `## ` heading is blank or a plain header line of the templates (so no HTML, comment, fence, quote, indented or unknown line can hide it from the owner), which only quick writes. The developer runs the issue's `Done when` before opening the PR, keeps the required checks green and reports its head. The CTO/CEO reads no diff and merges only on mechanical conditions through `pr_loop.py can-merge --unreviewed --head <sha>`, which refuses a PR that is not open, any judgment or stop on the PR by anyone on any head, a PR that links no issue, another repository's issue or an issue without `Pipeline: quick` in its header, a money path on the PR or a linked issue, and a head other than the given one; the script cannot know which head was reported, so the CTO/CEO takes the sha from the builder's report. A PR goes back to its builder at most 3 times: each return is a `Returned by CTO (...). PR #n at <sha>. Return K of 3.` comment on the PR, `decide` refuses a fourth, and then the CTO/CEO posts `Stopped by CTO` with the reason and reports to the owner; a clean rebase after another quick PR merged (`Rebase after #m.`) does not count, once per such PR and only when it merged after this PR's latest report or return (the newest of its last return, its creation and its head commit); an older merge or a time that cannot be read counts. After a confirmed merge or a stop the developer removes its worktree.
- **Refactor plan, planning only**: `playbook-refactor-plan` runs when a refactoring plan is asked for. The CTO/CEO passes the request to the planner/architect, who reads every repository in scope with its issues, analyses and plans and writes a bundle: a parent card, every new issue complete (title, labels, card fields, goal, analysis, recommended solution, owned files, dependencies, wave, `Done when`) and a disposition for every open issue, `remove` (reason, replacement) or `keep` (reason). The CTO/CEO does no work on it and posts the text unchanged with `refactor_bundle.py post`. The script checks the bundle (a disposition for every open issue, each new issue through the issue linter, references, waves and new-number placeholders) and prints a dry run with a digest; posting creates the new issues first, fills in their numbers, then closes each removed one as not planned with a short comment. It never deletes, closes only listed issues, never closes one with an open linked pull request (or whose links cannot be read, or that somebody reopened) and reports it, and a rerun reads the host and creates no duplicate. No code, branch, pull request or merge.
- **Plan, review, ship**: `playbook-plan` is CTO/CEO card → architect (bot or delegated worker) → one plan comment → back to the CTO/CEO → acceptance → stop. `playbook-review` posts one verdict on an existing PR and changes nothing. `playbook-ship` reviews a PR, fixes and re-reviews for at most 3 rounds (against the accepted plan when the issue has one), then merges it and closes its issue, or stops.
- **Merge rules**: a pull request merges only when it links an issue of its repository and every linked issue is approved. `github/scripts/issue_gate.py` checks it before work and before a merge. The `approvals` list in `github/assets/merge-rules.json` says what approves; shipped `["trusted_author", "owner_comment"]`. `trusted_author` approves an issue whose author can push: `gh api repos/<repo>/collaborators/<login>/permission` answers `role_name` admin, maintain or write with the base permission GitHub maps it to and `push` true; read, triage, custom roles, bots, a failed lookup or an odd answer approve nothing, and the author association (MEMBER, COLLABORATOR) is never used. The gh login needs write access to read those permissions. Anyone else's issue needs the owner's `Accepted by owner.` comment, for which the pipelines give one line that works in any shell; it approves only while the issue's body and title are as the owner saw them (GraphQL `lastEditedAt` and the newest `RenamedTitleEvent` before the comment), and an edit after it, or edit history that cannot be read, approves nothing until the owner accepts again. A closing reference to another repository's issue is refused by `issue_gate.py` and both forms of `pr_loop.py can-merge`. `owner_author` and `board_status` are off while agents share the owner's account; a missing, empty or unknown value refuses everything. Done, not planned and duplicate issues, refusing labels and refusing board statuses always refuse; without the scope for project boards the check goes on without them and says so, and any other failure to read the board refuses. Text signed by an agent never counts as the owner's.
- **Who may approve a merge**: `github/scripts/pr_loop.py` counts a refusal (FAIL, `Changes required`, `Stopped`) from an owner, member or collaborator, and a `Verdict: PASS` only when its author, in a comment or a review, can also push; a failed lookup drops a grant and never a refusal. `can-merge` needs such a PASS on the current head, not by the PR's writer, naming every commit its signer pushed; an `Accepted by CTO|CEO ... PR #n` approves nothing, and `decide` and `package_lint.py` refuse a new one. `decide` refuses a fourth review round; `can-remove` refuses a removal that could lose work (`--handover` for an open PR another agent takes). The reviewer runs a PR's code only when its author can push, by the same permission lookup.
- **No checks is not a failure**: `gh pr checks <n> --required` printing `no checks reported` with exit 1 means the repository has no checks; every pipeline that merges runs `--required` and reports "no checks".
- **Bots and agents**: new skill `bot-orchestration`. A bot only orchestrates: code, tests, deployment work, reviews and fixes and a plan's analysis go to the bot that holds the role or to the bot's own agent. A bot delegates to another bot with a handoff and gets a status back; a bot briefs its own agents; an agent reports only to its bot, and agents never message each other. The roles are architect, developer, tester, devops and reviewer; skills name roles only, and which bot holds which role is each team's own mapping skill, kept outside this repository. The developer bot takes the agent table's row for the issue's difficulty. Replies and status reports are short and carry only what the reader needs; long explanation belongs in the planner/architect's plans and issues, or where it is asked for. Five editable message templates and `message_lint.py`, which requires each rule line exactly. The `developer` skill no longer names two commands that do not exist.
- **One template per text, and the template is the rule**: every pull request body and every PR comment (verdict, CTO decision, fix, merge) has one template. The linters read sections, order and shapes from the `*.template.md` assets, so editing a template changes the requirement; `AGENT_TEMPLATES=<dir>` overrides them for one project. The GitHub templates for new repositories are copies written by `make docs`. A "Generated with" tool footer fails the lint.
- **Merge and PR checks**: the merge is `gh pr merge --rebase --match-head-commit` by the role the playbook names, never an admin override and never the PR's author. Rebase, not squash: a squash commit is authored by the account that opened the pull request, a rebase keeps the agent's name. `setup_repo.sh` allows rebase merges only.
- **Issue and comment skills**: added `write-issue` (kinds `epic`, `planning`, `package`; one catalog of task types, lanes, difficulties, priorities and flags) and `write-comment` (nine comment kinds; the plan comment is Code analysis, Core design decision with Stack and Rejected, Planned Packages or a wave table, Risks). `package_lint.py` checks `issue --kind` and `comment --kind` against the catalog; area labels are optional, a type label and a `Priority:` line are required, and an ID may end in one letter. Repo labels (`project/assets/labels.json`) are generated from the same catalog; `type:*`, `cli:*` and `agent:*` are gone.
- **Agent identity**: every commit is authored and committed under the agent's own name (`github/scripts/agent_identity.py`), and every issue, comment and PR body ends with `Created: <agent name>`; `package_lint.py` and `pr_lint.py` fail otherwise.
- **Work packages**: added the `work-package` skill: one fixed format for a delegable card. Issue `ID: title` with lane, difficulty and area labels and a fixed body (Goal, Read first, Owned files, Forbidden, Depends on, Done when, Branch and PR); branch `<id>/<slug>`; commits and PR `<type>(<id>): <summary>` with Summary, Files changed and Done-when evidence; `scripts/package_lint.py` checks all of it (`--self-test`). `github`'s `pr_lint.py` accepts a package branch.
- **Delegation**: the `delegate` skill gives one task to one Orca worker. `delegate.py` (also `swe-cli delegate`) reads the brief's row of the agent table and runs `orca orchestration worker-start` with its harness, model and reasoning effort; it has no option to choose any of them. Then the diff is read and the check run before anything lands. The `orca-cli` skill covers the Orca commands.
- **Configuration**: one `config.json`, `$SWE_CONFIG` else `~/.config/swe/config.json`, which only names where the agent table is. Nothing is read from the working directory, and `swe-cli config init` never overwrites.
- **Simplified CLI**: `swe-cli` is `update` (pull, rebuild, reinstall), `playbooks`, `agents`, `delegate`, `config`, `doctor` (git, gh, python3, Orca, harness CLIs and the agent table), `changelog show|check` and `name`.
- **Installer**: added root `install.sh` shell script for one-line remote or local installation across all detected AI agent harnesses.

## 1.0.0

First release. What it is today.

**Skills (41, in six groups)**
- Start and process: the `swe` router and its playbooks, principles, architect, how, why, tdd, deslop, blast-radius, interrogate,
  verify-create, verify-maintain, replay-test, formal-verify, correct, ketchup, reflect, github, project, and the changelog skill
  (a `CHANGELOG.md` entry in every PR, plus the project's `changelog/` directory).
- Roles of workflow agents: manager, planner, developer, reviewer, documenter, intake, integrator, ci-fixer, verifier.
- Languages: Go with Fiber v3 (default for APIs and services), Python (ML and data), Rust (performance), TypeScript (Next.js and
  Vite + React).
- Data: `db-migrations` (goose SQL files), `db-orm` (opt-in GORM for Go and SQLAlchemy 2 for Python behind the same port as raw SQL;
  tested on SQLite and PostgreSQL), `api-contract`, `data-pathway` (realtime pipelines) and `data-dagster` (batch and scheduled
  pipelines). Each of the two has a tested project template, an OTel metric contract, its timeframes and a Grafana dashboard
  checked against the metrics the code emits.
- Platform and observability: deployment-setup, service-logging, service-tracing, service-errors.

**Workflows and playbooks**
- `delivery` (several repos, interface first, merged in dependency order, no human), `lane`, `review`, `land`, and `docs` without a
  planner (`follow` or `rewrite`). Every code card runs code, docs, then the PR (`docs-sync` skill). `PROJECT.md` opens with a `# Map`.
- `play-*` shortcut skills (`play-deliver`, `play-bugfix`, `play-docs`, `play-cifix`, `play-rebase`, `play-changelog`, `play-verify`,
  `play-review`, `play-land`) and the `play` dispatcher. `play-solo` runs no workflow: the current harness plans, or takes an
  issue to a merged PR, with no delegation.

**Install**
- A plugin for Claude Code, Codex and oh-my-pi, and plain skills for 52 other harnesses (55 in all). `make install` installs into every detected
  harness, `make <harness>` into one, `make harness` lists them, `swe-cli update` pulls `main` and reinstalls.
- The plugin name, owner and version come from `plugin.env`; the default plugin is `swe`.

**`swe-cli` (`<plugin>-cli`)**
- `swe-cli init` makes a directory a project: `AGENTS.md` (the orchestrator's instructions), `PROJECT.md` (self-learned notes, under
  2000 words), `models.yaml` (the one place that defines the agents: cli, model and reasoning, for claude, codex, omp or opencode), `roles.yaml`, `workflows/`, `changelog/`, a
  `learn` skill and `project.yaml` (the repos); it asks for git URLs and clones them. `swe-cli project add` adds a repo later, and
  `swe-cli project update` refreshes the shipped files without overwriting yours.
- Any harness is the manager (`swe-cli orchestrate`); it answers questions itself and runs workflows for work. Workflows are YAML DAGs, one agent per node, each with only the skills of its
  role and the agent (cli, model, reasoning) it names: feature, bugfix, docs, card, docs-card, ci-fix, conflict, verify, changelog. Agents run in tmux or
  Orca sessions, one git worktree per card, and write reports to a tmp directory.
- The merge gate (`swe-cli merge`, run by `flow merge`) needs the verified head, green required checks, no conflict with `main` and a
  `CHANGELOG.md` entry in the PR (docs, chore, ci, test, style and build PRs and the `no-changelog` label are exempt). After each merge the
  PR is recorded in `changelog/<repo>.md` and `changelog/project.md`. `flow clean` removes every session, worktree, branch and tmp file.
- Also: `delegate`, `lane`, `doctor`, `context`, `models`, `changelog check|record|show`.

**Known limits**
- The Pathway pipeline tests have not been run against a real `pathway` install (the pure-logic tests and the metric checker have).
- The Dagster Dockerfile and compose stack have not been run.
